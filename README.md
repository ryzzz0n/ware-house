# 📦 WareHouse — система управления складом (WMS)

Backend на Go для учёта товаров на складе: от приёмки от поставщика до отгрузки получателю. Ведёт остатки по ячейкам, автоматически пишет историю движений и поддерживает инвентаризацию. В комплекте есть веб-интерфейс.

Проект учебный: курсовая работа, сделана на основе реальных процессов фулфилмент-склада.

## Что умеет

- **Справочники** — товары, поставщики, категории.
- **Топология склада** — участки (приёмка, сканирование, хранение, упаковка, отгрузка) и ячейки внутри них.
- **Приёмка и отгрузка** — документы с позициями. Остатки меняются только после проведения документа, и проведение можно отменить (сторно).
- **Остатки** — сколько товара лежит в каждой ячейке.
- **История движений** — записывается автоматически при каждой операции.
- **Инвентаризация** — сверка учётных остатков по участку.
- **Обработка** — задания на сканирование и упаковку с подсчётом потерь.
- **Авторизация** — регистрация, вход, JWT.

## Стек

| | |
|---|---|
| Язык | Go 1.22 |
| HTTP | Fiber v2 |
| ORM | GORM |
| БД | PostgreSQL (в Docker) |

## Быстрый старт

### Что нужно установить

- [Go](https://go.dev/dl/) 1.22 или новее
- [Docker](https://www.docker.com/) с Docker Compose
- Git

### 1. Клонировать репозиторий

```bash
git clone https://github.com/ryzzz0n/ware-house.git
cd ware-house
```

### 2. Создать файл `.env`

```bash
cp .env.example .env
```

Значения в `.env.example` уже совпадают с `docker-compose.yml`, так что для локального запуска ничего менять не нужно. Если меняете логин, пароль или имя БД в одном файле, поменяйте и в другом, иначе сервер не подключится к базе.

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DB_HOST` | `localhost` | Хост PostgreSQL |
| `DB_PORT` | `5432` | Порт PostgreSQL |
| `DB_USER` | `postgres` | Пользователь БД |
| `DB_PASSWORD` | `postgres` | Пароль БД |
| `DB_NAME` | `inventory_db` | Имя базы |
| `JWT_SECRETKEY` | — | Ключ подписи токенов. Любая случайная строка от 32 символов |

### 3. Запустить базу данных

```bash
docker compose up -d
```

Поднимутся PostgreSQL на порту `5432` и pgAdmin на http://localhost:5050 (логин `admin@admin.com`, пароль `admin`).

### 4. Запустить сервер

```bash
go mod download
go run main.go
```

При первом запуске таблицы создаются автоматически. Сервер работает на **http://localhost:8000**.

### 5. (Необязательно) Загрузить тестовые данные

Делайте это после первого запуска сервера, когда таблицы уже созданы:

```bash
docker exec -i postgres psql -U postgres -d inventory_db < seed.sql
```

> ⚠️ Скрипт **очищает** все складские таблицы перед загрузкой. Пользователи не удаляются.

### 6. Открыть интерфейс

Откройте `frontend/index.html` в браузере, зарегистрируйтесь и войдите. Для работы интерфейсу нужен интернет: React подгружается из CDN.

## Авторизация

Все эндпоинты, кроме `/register` и `/login`, требуют токен. Без него сервер вернёт `401 Unauthorized`.

**1. Регистрация**

```bash
curl -X POST http://localhost:8000/register \
  -H "Content-Type: application/json" \
  -d '{"email": "admin@test.com", "password": "123456"}'
```

```json
{ "message": "Register Successful" }
```

**2. Вход**

```bash
curl -X POST http://localhost:8000/login \
  -H "Content-Type: application/json" \
  -d '{"email": "admin@test.com", "password": "123456"}'
```

```json
{
  "message": "Login Successful",
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

Токен действует **72 часа**. Сервер также кладёт его в HTTP-only cookie `jwt`.

**3. Запрос с токеном**

```bash
curl http://localhost:8000/product \
  -H "Authorization: Bearer <token>"
```

## Как устроен учёт

Остатки нельзя поменять напрямую. Они меняются только через проведение документов, и каждое изменение пишется в историю движений. Благодаря этому всегда видно, откуда взялось текущее количество.

```
 Черновик (draft) ──confirm──▶ Проведён (confirmed)
        │                            │
        └──cancel──▶ Отменён ◀──cancel──┘  (для проведённого — сторно остатков)
```

| Операция | Что происходит при проведении |
|---|---|
| **Приёмка** `POST /receipt/:id/confirm` | Остатки в ячейке приёмки увеличиваются, движение `in` |
| **Отгрузка** `POST /shipment/:id/confirm` | Проверяется, хватает ли товара. Остатки в ячейке уменьшаются, движение `out` |
| **Отмена проведённого** `.../cancel` | Остатки возвращаются, движение `storno` |
| **Инвентаризация** `POST /inventory` | Позиции заполняются текущими остатками по ячейкам участка |
| **Закрытие инвентаризации** `POST /inventory/:id/close` | Расхождения (факт − учёт) применяются к остаткам |
| **Обработка** `POST /processing/:id/confirm` | Считаются потери: `отсканировано − упаковано`, движение `storno` |

Правила:
- Провести можно только черновик. Приёмку и отгрузку без позиций провести нельзя.
- Номер документа генерируется автоматически (`RCP-…`, `SHP-…`, `INV-…`, `PRC-…`), если не передан.

### Примеры запросов

Во всех примерах ниже нужен заголовок `Authorization: Bearer <token>`.

**Создать товар**

```json
POST /product
{
  "name": "Ноутбук ASUS VivoBook 15",
  "description": "15.6\", 16 ГБ ОЗУ",
  "price": 75000,
  "supplier_id": 1
}
```

**Создать участок и ячейку**

```json
POST /zone
{ "name": "Хранение A", "type": "storage" }
```

Типы участков: `inbound` (приёмка), `scanning` (сканирование), `storage` (хранение), `packing` (упаковка), `outbound` (отгрузка).

```json
POST /cell
{ "code": "A1-01", "zone_id": 1 }
```

**Принять товар на склад** (создать черновик и провести)

```json
POST /receipt
{
  "supplier_id": 1,
  "cell_id": 1,
  "note": "Поставка по договору №15",
  "items": [
    { "product_id": 1, "quantity": 20, "price": 70000 },
    { "product_id": 2, "quantity": 5,  "price": 12000 }
  ]
}
```

```
POST /receipt/1/confirm
→ { "message": "Приёмка проведена" }
```

**Отгрузить товар**

```json
POST /shipment
{
  "recipient": "ООО «Ромашка»",
  "cell_id": 1,
  "items": [
    { "product_id": 1, "quantity": 3, "price": 79900 }
  ]
}
```

Если товара не хватает, проведение вернёт ошибку:

```json
{ "error": "недостаточно товара ID=1: есть 2, нужно 3" }
```

**Задание на обработку**

```json
POST /processing
{
  "zone_id": 2,
  "items": [
    { "product_id": 1, "scanned": 10, "packed": 9 }
  ]
}
```

После `POST /processing/:id/confirm` для позиции будет посчитано `lost = 1`.

### Формат ответов

Сервер возвращает созданные и найденные объекты целиком. Служебные поля GORM пишутся с заглавной буквы: `ID`, `CreatedAt`, `UpdatedAt`, `DeletedAt`. Остальные поля в `snake_case`.

```json
{
  "ID": 1,
  "CreatedAt": "2026-11-07T23:10:00Z",
  "UpdatedAt": "2026-11-07T23:10:00Z",
  "DeletedAt": null,
  "code": "A1-01",
  "zone_id": 1
}
```

Удаление мягкое (soft delete): запись получает `DeletedAt` и пропадает из выдачи, но остаётся в БД.

### Ошибки

Ошибки приходят в едином формате:

```json
{ "error": "описание ошибки" }
```

| Код | Когда |
|---|---|
| `400 Bad Request` | Некорректный JSON, нечисловой ID, не заполнено обязательное поле |
| `401 Unauthorized` | Нет токена, токен невалиден или истёк; неверный email или пароль при входе |
| `404 Not Found` | Участок или документ с таким ID не найден |
| `500 Internal Server Error` | Ошибка БД или бизнес-правила (например, повторное проведение документа) |

## Известные ограничения

Честно о том, чего пока нет:

- Фактическое количество в инвентаризации нельзя изменить через API. Позиции создаются с `actual = expected`, поэтому закрытие пока ничего не корректирует.
- Отгрузка проверяет остаток товара **по всему складу**, а списывает из одной указанной ячейки. Если товар лежит в другой ячейке, остаток в указанной может уйти в минус.
- Задание на обработку фиксирует потери в истории движений, но не списывает их из остатков.
- Бизнес-ошибки (например, «можно подтвердить только черновик») возвращаются с кодом `500`, хотя правильнее было бы `409`/`422`.
- Нет ролей: любой авторизованный пользователь может всё.
